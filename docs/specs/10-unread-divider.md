# 10. 안 읽음 구분선과 첫 안 읽음 위치로 이동

우선순위 P0 / 추천 모델 sonnet / 예상 1.5h / 스키마 변경 없음 / 07과 MessageList.tsx 충돌, 07 이후 배정

## 1. 기능 설명
근거: 이 항목은 이번 루프에서 직접 관찰하지 못했다(브라우저 불가). 첫 분석 [R2]에서 안 읽음 페이지와 배지는 있는 것으로 확인했고, 구분선은 Slack 일반 동작 지식 기반 추정이다. 검증 필요: 구분선 문구, "N개의 새 메시지" 바, 사라지는 시점.
현재 우리 상태: 읽음 위치(ChannelRead.lastReadMessageId), 배지, `/read`, `/read/baseline`, `/unread` API, 안 읽음 페이지는 있다(routes/channels.ts 806~896행, Messages/UnreadsPage.tsx). 채널을 열면 곧바로 최신 위치로 가며 **어디까지 읽었는지 시각적 구분이 없다**.
1. 채널/DM/그룹 DM을 열 때 서버의 읽음 기준점(열기 직전 값)을 고정해 두고, 기준점 다음 메시지 앞에 가로 구분선 + "새 메시지" 라벨을 그린다.
2. 안 읽은 메시지가 화면 위쪽에 있으면 상단에 "N개의 새 메시지 · 위로 이동 / 읽음으로 표시" 바를 보인다. 클릭하면 구분선 위치로 스크롤. 구분선이 화면에 보이면 바는 사라진다.
3. 스크롤이 끝까지 내려가거나 창에 포커스된 채 최신 메시지를 보면 읽음 처리(기존 동작 유지)하되, **구분선은 그 채널을 떠나거나 새로고침할 때까지 유지**한다(읽자마자 사라지면 위치를 잃는다).
4. 내가 방금 보낸 메시지는 구분선 위로 간주(내 메시지는 안 읽음에서 제외).
5. "읽지 않음으로 표시"(메시지 U)를 하면 그 메시지 앞에 구분선이 생긴다.
6. 안 읽음이 하나도 없으면 구분선 없음. 안 읽음이 로드 범위(50개) 밖으로 많으면 구분선 대신 상단 바만(클릭 시 `around`로 해당 위치 로드).

## 2. 화면 흐름
1. 채널 클릭 -> `GET /channels/:id`가 내려주는 `lastReadMessageId`(또는 기존 안 읽음 수 계산 필드)를 스토어에 `dividerAfterId`로 저장 -> 메시지 로드 -> 구분선 렌더, 구분선 위치로 스크롤(첫 안 읽음이 맨 위에 보이도록, 최신이 한 화면 안이면 바닥).
2. 새 메시지가 실시간으로 도착(내가 해당 채널을 보고 있고 포커스 있음) -> 구분선은 움직이지 않음.
3. 채널 이탈 -> `dividerAfterId` 폐기. 재진입 시 새 기준점.
4. 모바일 레이아웃에서도 동일(바 문구 짧게).

## 3. 데이터 모델
없음. 기준점은 이미 있는 `ChannelRead.lastReadMessageId`와 그룹 DM·DM의 읽음 구조를 사용한다. DM 읽음 저장 구조가 채널과 다른 경우 확인 필요(`routes/dms.ts`, `dmGroups.ts`의 read 처리).

## 4. API / 이벤트
- 열 때 기준점이 필요: `GET /channels/:id` 응답에 `lastReadMessageId`가 이미 있는지 확인하고 없으면 추가(DM/그룹 DM 조회 응답에도 동일 필드). **중요**: 응답은 읽음 처리보다 먼저 계산한 값이어야 한다(레이스: 열자마자 `/read`가 호출되면 기준점이 최신으로 덮인다). 프런트가 열 때 값을 캡처한 뒤에 `/read`를 호출하도록 순서 보장.
- 이벤트 변경 없음. 다른 탭에서 읽음 처리해도 현재 탭 구분선은 유지.
- Slack 대응(추정): `conversations.mark`, 소켓 `channel_marked`. 확인 필요.

## 6. 완료 기준
- `lib/unread.ts` 단위 테스트: 기준점 중간/마지막/없음, 내 메시지 제외, 삭제된 메시지 건너뜀.
- 컴포넌트 테스트: 안 읽음 3건 있는 채널을 열면 구분선이 정확히 한 번, 첫 안 읽음 바로 앞. 읽음 처리 후에도 유지, 채널 이동 후 복귀하면 사라짐.
- "U로 읽지 않음 표시" 후 구분선 위치가 해당 메시지 앞.
- 안 읽음이 60개일 때 상단 바 클릭이 around 로드로 이동(백엔드 around는 이미 구현).
- 백엔드 회귀: 기존 unreads 테스트 전부 통과, 열기 응답의 기준점이 읽음 처리 이전 값.
- CRUD 확인: 사용자 B로 메시지 3개 작성 -> A가 열기(구분선) -> 읽음 -> 재진입(구분선 없음) -> B가 1개 더 작성 -> 구분선이 새 1개 앞.
